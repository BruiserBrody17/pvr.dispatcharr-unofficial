#### Support Kodi 22 (Piers): the addon is refused by Kodi 22 RC1

**Opened 2026-10-12, from a user's report: on Kodi 22 RC1 (a Windows laptop) the addon "is not supported yet".** Kodi 22's PVR API is 9.2.0 with a minimum of 9.2.0 (Omega, which this branch builds against: 8.3.0, minimum 8.2.0), and its main and general APIs moved to 2.0.4 and 1.0.5, so the addon's declared imports and an Omega-built binary are refused outright; it must be rebuilt against Kodi 22's headers. A syntax-only compile of every `src/` file against the Piers dev-kit headers (branch `Piers`, 2026-10-11) gave six errors, all in `PVRDispatcharr.h`: the five recorded-stream overrides (`OpenRecordedStream()` now also returns a stream id, `ReadRecordedStream()`, `SeekRecordedStream()`, `LengthRecordedStream()` and `CloseRecordedStream()` take it), and `GetChannelStreamProperties()`, which gains a `PVR_SOURCE` argument (regular live, or playing a guide entry as live). The C++ wrapper hides the rest of the change (the C structs now hold string pointers instead of fixed arrays, EDL and timer-type lists are heap arrays), so most of `src/` compiles unchanged. What the port still needs: (1) the stream id means Kodi may hold more than one recorded stream open, but `DispatcharrClient` keeps one `m_recordingStream` and one `m_inProgressRecordingStream`, so either the state is keyed by id or a second open is refused deliberately; (2) the glue harness's stub and driver use the C structs directly and need the new shapes; (3) new optional calls worth a look, `GetRecordedStreamTimes()`, `IsRecordedStreamRealTime()` and `PauseRecordedStream()`, which bear on how an in-progress recording behaves in the player and on the open item about watching live while a recording runs; (4) `addon.xml.in` import versions, `KODI_COMMIT` and `KODI_BRANCH` in the workflow, and the Windows, Android and CoreELEC builds against Piers (`docs/BUILDING.md` notes `coreelec-22` tracks it); (5) the branching policy in `CLAUDE.md`: branch `Piers` off `Omega` once the source differs, keep `Omega` as the Kodi 21 maintenance branch, and decide how fixes flow between them (merge `Omega` into `Piers`; the six signatures are the only divergence so far). Confirm live on Kodi 22 RC1 with a Windows build: the addon loads, channels and guide appear, a live channel plays in each timeshift mode, a recording plays (completed and in progress) and seeks, and the timers dialog works.

### Design decision needed

#### A channel that is slow to start: Kodi gives up after 20 seconds in Off and Local live mode

**Opened 2026-10-12, from a user's report: two channels take a while to start, a playback error appears, and pressing OK and opening the channel again plays it at once.** The reporter's answer on 2026-10-13 (timeshift Off, an Android device, two free-to-air HLS channels, logs from Kodi and from Dispatcharr) showed the cause is not in the addon's open path. There are two separate causes, one per live mode; the first is open, the second is fixed and waits for a release.

**Off and Local mode (open, decision on hold since 2026-10-13).** The addon only hands Kodi the proxy URL (`BuildLiveChannelStreamProperties()`), and Kodi opens it itself: `CFileCache::Open ... failed to open`, preceded by `CCurlFile::CReadState::FillBuffer ... Timeout was reached(28)`, 20.0 to 20.6 s after the open began, every time; the immediate second open plays. Dispatcharr's log for the same two opens: the first client registers at once and the channel moves `initializing -> connecting`, the proxy's stream generator then sits at `channel_ready=False` and sends the client nothing, and the buffer fills (`connecting -> active`) 24 s after the request for one channel and 21 s for the other, so the first byte arrives after Kodi has given up. The second open lands within the proxy's 5 s shutdown delay after Kodi's first client left, joins the running channel and gets data in half a second. So the stall is the interval between Dispatcharr accepting the client and having a buffered chunk (here ffmpeg opening an HLS master playlist and its variants; the reporter links it to the profile's stream mapping, which has not been checked here). The 20 s is Kodi's `curllowspeedtime` default (`m_curllowspeedtime = 20` in `AdvancedSettings.cpp`, read from `advancedsettings.xml` as `<network><curllowspeedtime>`); the only per-URL timeout option `CCurlFile` parses is `connection-timeout`, which sets the connect timeout, not this one, so the addon cannot lengthen it through the URL. An earlier version of this item said the proxy answers at once with keep-alive packets while a channel initialises; it does not for this server version, the generator sent nothing for 20 s.

Two ways forward, nothing built:
- **(a) Document the Kodi setting as the workaround.** Cheap, global to all of Kodi's curl reads, and not something the addon can set. **Checked live on 2026-10-13** (lab VM, a real Kodi, timeshift Off, a forwarder in front of the server that held the proxy stream request for 28 s before sending anything and passed everything else through): with Kodi's default the open failed with the playback-failed dialog at 20.9 s; after adding `<advancedsettings><network><curllowspeedtime>60</curllowspeedtime></network></advancedsettings>` to `advancedsettings.xml` and restarting Kodi, the same open played, at 35.7 s on the first try. The lab was restored afterwards.
- **(b) Warm the channel in `GetChannelStreamProperties()` when the mode is Off or Local.** The addon opens the proxy URL itself, waits for the first bytes (bounded, about 30 s), and keeps that connection until Kodi has attached, since closing the only client would start the 5 s shutdown (or an immediate stop with a delay of 0) and make Kodi's open pay the full start again. It blocks whichever Kodi thread calls it, which has to be measured first (the Server-side mode's open already costs a UI freeze, see "Cut the time a stalled open holds Kodi's UI"), and it adds a client to the channel for the length of the warm-up.

The decision between them is on hold (2026-10-13); the workaround is not in the README.

**Server-side mode (fixed on `Omega` as `142772f`, 2026-10-13; closes once a tagged release carries it).** The live cold-start loop (`OpenLiveTimeshiftStream()`) tried `get_live_manifest` 30 times, 500 ms apart, so it waited about 15 s for the first segment before failing with "no live playlist"; a channel whose provider took longer to deliver its first full segment (plus the plugin's segment length) outlasted it, and the second try worked because the failed open had deregistered the viewer while Dispatcharr kept the channel up for its shutdown delay. The fix uses what the plugin already says: it answers `fatal` once ffmpeg has exited, so a non-fatal "live playlist not found" means the channel is still starting. `RefreshLiveManifest()` reports that case (`pluginAnsweredNotReadyOut`) and the loop's limit is `ColdStartTryLimit()`: 60 tries (about 30 s, chosen over 45 s to halve the worst-case Stop freeze) while the plugin keeps answering it, the old 30 and the old 45 s budget for a try that got no answer (a silent server); the give-up warning is now logged for either reason (it used to be logged only when the wall-clock budget ran out). **Reproduced and checked live on 2026-10-12 and 2026-10-13** (lab VM, Server-side mode, a forwarder in front of the server answering the plugin's own "live playlist not found" reply for a set time after each `start_buffer` and passing everything else through, the plugin's file-server port forwarded as well since segment URLs use the configured host): before the change, 25 s of "not ready" made the addon stop the buffer 15.1 s after starting it and Kodi showed its playback-failed dialog, while opening again with the delay off played at once; after it, 25 s of "not ready" played **on the first try, at 29.7 s**; with 40 s it gave up at 29 s, logged `no live playlist after 60 tries and 29s, giving up`, and showed the dialog at 31.3 s, and opening again with the delay off played in 5.2 s; a real channel whose ffmpeg had died stopped the wait on the plugin's `fatal` answer after about 24 s, as designed. **The freeze this costs, measured:** Stop pressed 5 s into a 40 s "not ready" open held Kodi's main thread for 26.4 s, until the loop gave up (JSON-RPC answered at once; any call needing the UI thread blocked); see the closed entry "Cut the time a stalled open holds Kodi's UI". A Server-side user who still sees this should send the error `failed to open server-side timeshift stream for channel <uuid>: live playlist not found -- ...` (a slow start longer than about 30 s) or `ffmpeg exited before producing any segments` (the plugin's own fatal answer, a provider limit or a bad stream, which waiting does not fix). The reporter has not been able to confirm on a build that has the fix: it is not in a tagged release yet.

#### Watching live while a recording runs on the channel starts a second buffer

**Opened 2026-10-12, from a user's report (Server-side mode; they were recording a programme, then tuned the channel and answered "live" at Kodi's "play recording or tune to live" prompt).** `GetChannelStreamProperties()` and `OpenLiveStream()` never look for a recording on the channel: in Server-side mode every live open starts (or joins) the timeshift-buffer plugin's own buffer for it, a second ffmpeg and a rolling buffer on disk next to the recording's own. The user's expectation, from Tvheadend: the in-progress recording already allows pause and rewind, so watching live should use it and start no buffer. The cost today is the extra process and disk, not an extra provider connection: **confirmed live 2026-10-13** (lab Dispatcharr 0.32.0, Server-side mode, an instant recording started through Kodi's `PVR.Record`, then the same channel tuned live and "Switch to channel" chosen at Kodi's prompt). `/proxy/ts/status` listed one channel with one client (the recording's `Dispatcharr-DVR/recording-<id>`) before the live open and, after it, the same channel with the same stream id, the same M3U profile and the same `started_at` (so the upstream connection was not reopened) and two clients: the recording and the buffer's ffmpeg (`Lavf/...`). The recording and the buffer are clients of the channel's one proxy stream, so this is one provider connection, not two. Playback advanced normally. The recording was deleted afterward (204, then 404) and the proxy showed no active channels; the VM was restored. The idea is feasible in outline, since the addon already plays an in-progress recording with seek and pause (`OpenInProgressRecordingStream()`), but Kodi plays a channel through the live-stream callbacks (`OpenLiveStream()`, `ReadLiveStream()`, `SeekLiveStream()`, `GetStreamTimes()`) and a recording through the recorded-stream ones, so the live path would have to delegate to the recording's reader and report stream times for it. The blocking questions are semantic. (1) **The recording ends** at the programme's end plus post-padding, so a viewer who chose "live" reaches the end of the stream mid-channel; handing over to a timeshift buffer without a gap (or without Kodi leaving the channel) is not something the callbacks obviously allow, and a reopen drops the viewer to the channel with a gap. (2) **The recording can be stopped or deleted** (from Kodi or Dispatcharr) while someone watches it as live, which ends a stream they never asked to end. (3) **The live edge** of a recording is a segment or two behind the real one, as the timeshift buffer's is; rewind reaches back only to the recording's start, which is probably what a viewer wants. (4) **Tvheadend parity, checked in source 2026-10-13 (`docs/PVR_HTS_COMPARISON.md`, "Watching live while a recording runs"):** the report says Tvheadend plays the recording instead of starting timeshift when "live" is chosen over a recording; neither pvr.hts nor Tvheadend's timeshift code has any such behavior. pvr.hts asks for the maximum timeshift on every subscribe regardless of the DVR state, and the server's timeshift is per subscription and never looks at recordings. What can look like it: Tvheadend's optional on-demand timeshift (buffered only from the first pause), and the "Play recording" answer, which opens the in-progress file with pause and seek and ends playback when the recording ends. So Tvheadend is not a model for delegation with a handover; the closest it comes to the report's expectation is on-demand buffering. Options: leave it (it works, it costs a process and disk); a setting that plays the channel plainly (no pause or rewind) when a recording already runs on it, which saves the buffer but loses the pause the user wants; or the delegation above, preceded by a live experiment of what Kodi does when a live stream's reader returns end-of-stream mid-playback (does it leave, retry the open, or hold the player?), which decides (1). **Added 2026-10-13, from the reporter's follow-up and a read of Kodi's source (Omega tree, not yet confirmed live).** The reporter's expectation, restated: answering "live" should use the recording, not start a buffer, because the recording already allows pause and rewind; they used Tvheadend before, where choosing live while joining a recording starts no timeshift and plays from the recording. What the addon can see: nothing of the prompt. The prompt is Kodi's own (`CPVRGUIActionsPlayback::SwitchToChannel()`: "Play recording" or "Switch to channel"); "Switch to channel" starts an ordinary live open, indistinguishable from any other. The addon can find the recording itself (its recordings cache knows which are in progress on the channel). Today's workaround: answer "Play recording", which opens the in-progress recording with pause, seek and rewind, and skip to its end. **The end-of-stream question, answered from source:** when a live stream's read returns 0, `CInputStreamPVRBase::Read()` sets end-of-file, `CInputStreamPVRChannel::NextPVRStream()` then asks for a reopen, and `CVideoPlayer` closes the demuxer and breaks out of its loop, so **playback ends** (it neither retries nor holds). A live view delegated to a recording would therefore drop the viewer out of the channel when the recording ends (the programme's end plus post-padding), which is the common case for someone watching a programme live to its end; a plain delegation is not acceptable on its own. The addon controls the bytes `ReadLiveStream()` returns, and both the live buffer and an in-progress recording are byte-addressable lists of MPEG-TS segments in this addon, so a handover is possible in principle: start a timeshift buffer shortly before the recording ends and keep appending its segments to the same live address space (a discontinuity in the TS at the splice, which Kodi's demuxer already tolerates at the buffer's own restarts; to be confirmed). Open design choices: (a) leave it, with the workaround documented; (b) delegation with that handover (the largest option: detection, a live-callback wrapper around the in-progress reader, stream times, and the splice); (c) a setting that plays the channel plainly (no pause or rewind) while a recording runs, saving the buffer and losing the pause. **An on-demand buffer (start it at the first pause or seek) was analysed 2026-10-13 (`docs/TIMESHIFT.md`, "An on-demand live buffer: what it would take"; measured, nothing built):** the plugin can be started late with no change (first manifest 2.9 to 4.1 s after the call, a late buffer begins with roughly 10 s of recent past), but the addon would need a direct live reader that does not exist, a `PauseStream()` hook it does not implement, and a splice from the direct stream to the buffer; it saves a light `-c copy` ffmpeg and disk per viewer and gives the reporter only about 10 s of rewind at first, not the recording's, so it fits the cost they noticed and not the pause and rewind they want. Confirm the end-of-stream behavior live first (a live reader returning 0 mid-playback; the glue harness's ended-buffer knob and a real Kodi would do), then the splice. Confirm live with a recording running on a channel and the channel opened as live: today's behaviour is a buffer in `list_buffers` for that channel (the baseline to record), and after any change none, with pause, rewind and the recording's own end handled as decided.

#### Let a series rule's description filter be set from Kodi

**Opened 2026-10-10, from the pvr.hts comparison; narrowed 2026-10-13 when the title half was done (`docs/CLOSED_ITEMS.md`, "Let a series rule made in Kodi match the title loosely").** What is left is the rest of the original item. pvr.hts searches the full EPG text per rule (`PVR_TIMER_TYPE_SUPPORTS_FULLTEXT_EPG_MATCH`, Kodi's "Fulltext EPG search" checkbox); Dispatcharr's series rule has `description` and `description_mode` (`contains` by default, or `search` or `regex`; `docs/DISPATCHARR_SOURCE_REVIEW.md`), and `AddTimer()` still creates every rule with them blank, so a rule made from Kodi never filters on the description, and an edit from Kodi keeps whatever the rule had. Decisions: whether the full-text flag maps to "also match the description", with the search string as `description` (the checkbox means that in Kodi, and the title filter would then be what, the same string or blank?), which `description_mode` it uses (a second setting, or follow the title setting), and whether regex is ever offered (the addon cannot evaluate PostgreSQL regexes, so a regex rule is left unlinked from its recordings, `docs/CLOSED_ITEMS.md`). Nobody has asked for it; the title setting covered the case the reporter-style requests had in mind. Confirm live by creating a rule from Kodi with the flag set and checking what Dispatcharr stores and which programmes it schedules.

#### A silent upstream stall ends playback about 48 s before Dispatcharr heals it

**Opened 2026-10-13, from the measurements for the event-hooks item (`docs/TIMESHIFT.md`, "Upstream failover on a buffered channel: measured").** On a channel with a second stream, a first stream that keeps its connection open and sends nothing makes Dispatcharr raise `channel_reconnect` at about 28 s and switch streams at about 58 s (reason `health_monitor`, the buffer's ffmpeg surviving), but a Kodi viewer in Server-side mode loses playback 10.4 s after the stall began: at the live tail `ReadLiveTimeshiftStream()` waits for a new segment up to a budget of about three segment durations (6.25 s with 2 s segments), handing the read back every one to two seconds so a Stop can land, and then ends the stream. A dropped connection is not affected (failover in about a second, playback never stopped). A viewer who re-tunes at once rejoins the same buffer, which has no new data until the switch, so nothing is gained before 58 s. The short wait is deliberate and is bounded by Kodi, not only by the addon: the stalled-streams review (`docs/CLOSED_ITEMS.md`, "One stated stalled-stream rule per read path, with one threshold") found that Kodi tolerates only a few zero-byte reads in five or six seconds and ends playback on a read that keeps failing, and a read that blocks for a minute makes a Stop hold Kodi's UI for that minute (the opposite of the 2026-10-13 fix that cut a stalled open to its first timed-out try). Options: (a) leave it, since a stall is the provider's failure and the viewer learns of it quickly; (b) block the tail wait longer in Server-side mode (say 60 to 70 s) and accept a Stop that takes that long, which is a step back from the open-time work; (c) keep Kodi fed during the wait (the addon controls the bytes `ReadLiveStream()` returns, but nothing it could send is valid video for the gap, and a splice at the end has the discontinuity questions of the on-demand-buffer analysis); (d) document that Dispatcharr's own stall detection (its proxy settings; which setting and how low it can go were not checked) decides how long a silent stall lasts, so a user who wants the failover inside Kodi's patience can shorten it on the server, with no code change. Not measured: a stall with no second stream (the same ending, with nothing to heal it), a real provider's stalls, and what Kodi does when the tail wait returns zero bytes instead of `-1` for longer. Decide the intent first (is a stall with a backup stream expected to be survived?), then confirm live with the same two-stream test channel (the drop-and-stall source used for the measurement is a few lines of Python behind an ffmpeg test pattern).

### Known gaps, deliberately deferred

#### Wake-on-LAN for a Dispatcharr host that sleeps

**Opened 2026-10-10, from the pvr.hts comparison; deferred.** pvr.hts sends a Wake-on-LAN packet to a configured MAC
address (`kodi::network::WakeOnLan`, part of Kodi's addon API) before its first connect, for a backend that sleeps when
idle. Cheap to add as an optional setting, but Dispatcharr is usually a container on an always-on host and nobody has
asked. Pick it up if a user reports a sleeping server; the whole change is the setting, one call before the first
request, and a note in the README.

#### Multiple Dispatcharr servers from one Kodi

**Opened 2026-10-10, from the pvr.hts comparison; deferred.** Kodi 20 and later let one PVR addon run several backend
instances (`instance-settings.xml` next to `settings.xml`); pvr.hts added it in 20.4.0 with a one-time migration of the
pre-instance settings in its `addon.cpp`. This addon is one instance, and `docs/API_NOTES.md`'s "Single-instance
assumption: partially hardened, not fully" section lists what else assumes that (the API-key persistence, the recurring
rule tag). Worth doing only if someone runs two Dispatcharr servers, or wants two accounts (admin for the companion
plugins, non-admin otherwise) against one server from one Kodi; the migration step and the per-instance settings
handling in `OnAddonSettingChanged()` are the work. Not started.
