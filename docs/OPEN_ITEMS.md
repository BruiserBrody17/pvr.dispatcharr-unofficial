#### Support Kodi 22 (Piers): the addon is refused by Kodi 22 RC1

**Opened 2026-10-12, from a user's report: on Kodi 22 RC1 (a Windows laptop) the addon "is not supported yet".** Kodi 22's PVR API is 9.2.0 with a minimum of 9.2.0 (Omega: 8.3.0, minimum 8.2.0), so an Omega-built binary is refused outright and the addon has to be rebuilt against Kodi 22's headers. **Done on the `Piers` branch (2026-10-14), pending the live check:** the six overrides whose signatures changed (`GetChannelStreamProperties()` gained `PVR_SOURCE`; the five recorded-stream calls take or return a stream id), a recorded-stream registry keyed by that id with `SetSupportsMultipleRecordedStreams(true)` and the per-id `IsRecordedStreamRealTime()`, `PauseRecordedStream()` and `GetRecordedStreamTimes()` (`docs/API_NOTES.md`), the glue harness on Kodi 22's ABI (`tests/glue/kodi_abi.h`), CI building against the `22.0rc1-Piers` commit, and the branching, versioning and tagging policy (`docs/BRANCHES.md`). `addon.xml.in` needed no import edit: the `kodi.binary.*` imports are generated by Kodi's build (`@ADDON_DEPENDS@`), and the optional `inputstream.ffmpegdirect` import's `3.0.0` is satisfied by Kodi 22's `22.2.10`. **Live check on Kodi 22.0-RC1, Windows, 2026-10-15** (a portable Kodi 22 profile beside the Kodi 21.3 install, the build `28ea2eac1eb` that CI pins, and the addon zip CI built from this tree; Kodi 21.3 on the same server as the control): the addon loads (no "not supported"), the built `addon.xml` declares `kodi.binary.global.main` 2.0.3 and PVR 9.2.0, and it connects. `tools/kodi_smoke_test.py`: 11 passed, 0 failed, 4 skipped (nothing recording, no catch-up programme found, and server-side timeshift not seekable on the first, placeholder, channel). Server-side timeshift on real channels plays and is seekable, and Kodi's seeks reach the addon and land where it serves them (checked in the addon's debug log: the JSON-RPC `time` of a live channel follows wall time on Kodi 21.3 and 22 alike and cannot show a seek). Completed recordings play and seek. An in-progress recording plays, its total time grows as it records, a seek to the live edge lands at the tail, and when the recording stops during playback the player ends cleanly. Kodi 22 itself opens a second stream of a recording that is already playing (within the same second as the first open): stream ids 3 and 4, `openStreams=2`, closed in turn, back to 0. Off mode has a problem on Kodi 22 (the next item). **Still open:** (1) the rest of the live check: Local mode (`inputstream.ffmpegdirect` was not installed in the profile), the timers dialog, catch-up playback, and the Off-mode item below; (2) the macOS, Android and CoreELEC builds against Kodi 22, which `docs/BUILDING.md` lists the known differences for but nobody has run, including what version and zip name CoreELEC gives a package whose `PKG_VERSION` carries the `-Piers` suffix; (3) raise the pinned Kodi commit from RC1 to 22.0 final when it ships; (4) the first `Piers` release (`0.14.0`, unreleased in `CHANGELOG.md`), which needs the user's go-ahead for the version, the tag and any push to GitHub. ### Architectural / concurrency

### Design decision needed

#### Kodi 22 RC1 probes an Off-mode stream's MIME type, and Dispatcharr answers the real request with 503

**Opened 2026-10-15, from the Kodi 22 live check.** With `live_timeshift_mode` Off (the default) the addon hands Kodi the channel's proxy URL with `mimetype=video/mp2t`. On a channel the server is not already streaming, Kodi 22.0-RC1 opens it **three times**: a `HEAD ...?mimetype=video%2fmp2t` (Dispatcharr answers 405), a `GET` of the same URL (200, after the server has started the channel, a few seconds), and then the real `GET` without the query, which Dispatcharr answers **503 with `Retry-After: 1`** within milliseconds. Kodi gives up ("error opening"), so the first attempt to play a channel nobody is watching fails; an immediate second attempt works because the channel is by then running (seen 4 of 4 cold attempts on Kodi 22, an immediate retry succeeded each time). Kodi 21.3 on the same server and channel sends one plain `GET` and plays (captured on the wire with `pktmon`, server idle in both). Plain `curl` with Kodi's headers gets 200 every time, so the request headers are not the cause. Kodi 22's `CPVRPlaybackState::OnPreparePlayback()` sets the MIME type and turns the content lookup off exactly as Kodi 21's does, so whichever path sends the probe is Kodi's, not something the addon's properties control; I did not find it in Kodi's source. The server-side and Local modes do not use the proxy URL this way and were not affected. Options: (a) report it to Kodi (it affects any addon that returns a plain URL) and document "retry once" in `docs/TROUBLESHOOTING.md` until a Kodi 22 build fixes it; (b) have the addon start the channel itself before returning the URL in Off mode (a `GET` that is closed again once the server has begun streaming, so Kodi's request meets a running channel), at the cost of a request and a few seconds in `GetChannelStreamProperties()` and a client connection the server must tidy up; (c) both. Needs a decision before the first `Piers` release, since Off is the default.

### Known gaps, deliberately deferred

#### Wake-on-LAN for a Dispatcharr host that sleeps

**Opened 2026-10-10, from the pvr.hts comparison; deferred.** pvr.hts sends a Wake-on-LAN packet to a configured MAC
address (`kodi::network::WakeOnLan`, part of Kodi's addon API) before its first connect, for a backend that sleeps when
idle. Cheap to add as an optional setting, but Dispatcharr is usually a container on an always-on host and nobody has
asked. Pick it up if a user reports a sleeping server; the whole change is the setting, one call before the first
request, and a note in the README.

#### Multiple Dispatcharr servers from one Kodi

**Opened 2026-10-10, from the pvr.hts comparison; deferred.** Kodi 20 and later let one PVR addon run several backend
instances (`instance-settings.xml` next to `settings.xml`); pvr.hts added it in 20.4.0 with a one-time migration of the
pre-instance settings in its `addon.cpp`. This addon is one instance, and `docs/API_NOTES.md`'s "Single-instance
assumption: partially hardened, not fully" section lists what else assumes that (the API-key persistence, the recurring
rule tag). Worth doing only if someone runs two Dispatcharr servers, or wants two accounts (admin for the companion
plugins, non-admin otherwise) against one server from one Kodi; the migration step and the per-instance settings
handling in `OnAddonSettingChanged()` are the work. Not started.

#### Two streams of one in-progress recording each poll its manifest

**Opened 2026-10-14, with the multiple-recorded-streams work on `Piers`; deferred.** Kodi 22 may hold two streams of the
same recording open (`docs/API_NOTES.md`, "Single-instance assumption"), and each `InProgressRecordingStreamState`
refreshes the recording's HLS playlist and looks the recording up on its own, about every half second while it is read
and on every `GetRecordedStreamTimes()` poll. They share the sized-segment cache (`m_inProgressSegmentCache`) but not
the refresh itself, so the request rate doubles for that recording. Nothing is known to break, and nothing in Kodi
opens two streams of one recording on purpose that this project has found; pick it up if a log shows it, by sharing the
playlist fetch and the lookup per recording id behind the throttle that already exists.
