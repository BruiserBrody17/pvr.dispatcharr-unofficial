### Needs a live check

#### A channel that is slow to start makes the live open give up after about 15 seconds

**Opened 2026-10-12, from a user's report: two channels take a while to start, the addon appears to give up, a playback error appears, and pressing OK and opening the channel again plays it at once; the user has set Dispatcharr to keep a channel running a while after its last client leaves.** The live cold-start loop (`OpenLiveTimeshiftStream()`) tries `get_live_manifest` 30 times, 500 ms apart, so it waits about 15 seconds for the first segment before failing with "no live playlist"; a channel whose provider takes longer to deliver its first full segment (plus the plugin's segment length) outlasts it. The second try works because the failed open deregistered the viewer, but Dispatcharr kept the channel up for its shutdown delay and the next buffer joins a stream that is already flowing, which matches the report exactly. Dispatcharr's stream endpoint also answers at once with keep-alive packets while a channel initialises (the proxy's stream view), so ffmpeg is reading data the whole time and the plugin shows no failure to react to. Unconfirmed: which live-timeshift mode the user runs (with Off or Local the addon hands Kodi the proxy URL and the playback error is Kodi's, not this loop's), and whether the log says "no live playlist after ... giving up" or a fatal ffmpeg exit. Ask for the log line and the mode. If it is this loop, the choices are a longer wait (it cannot just be raised: a Stop during an open freezes Kodi's UI until the open returns, see the closed entry "Cut the time a stalled open holds Kodi's UI", so 45 seconds of wait is 45 seconds of freeze), a wait that grows only while there is evidence the channel is coming up (the plugin reports whether ffmpeg is alive; an admin account can read the channel's state from `/proxy/ts/status`), or a setting for how long a channel may take. **Reproduced live on 2026-10-13** (lab VM, Server-side mode, a forwarder in front of the lab server answering the plugin's own captured "live playlist not found" reply for the first 25 s after the buffer start): the addon made all 30 tries, stopped the buffer 15.1 s after starting it, and Kodi showed its playback-failed OK dialog; opening again with the delay off played at once. The log line to ask a user for is the error `failed to open server-side timeshift stream for channel <uuid>: live playlist not found -- ...`. A gap found on the way: the warning `no live playlist after N tries and Ns, giving up` is logged only when the wall-clock budget runs out, so a give-up after the 30th try logs nothing of its own. What is still unknown is the reporter's mode and log, and the choice among the three options above. **Change on the branch `slow-start-live-open`, not merged (2026-10-12):** the second option, using what the plugin already says: it answers `fatal` once ffmpeg has exited, so a non-fatal "live playlist not found" means the channel is still starting. `RefreshLiveManifest()` now reports that case (`pluginAnsweredNotReadyOut`) and the loop's limit is `ColdStartTryLimit()`: 60 tries (about 30 s, chosen over 45 s to halve the worst-case Stop freeze) while the plugin keeps answering it, the old 30 and the old 45 s budget for a try that got no answer (a silent server). The give-up warning is now logged for either reason. The late-start glue scenario fails on the old code at 15.0 s and passes at 25 s; the silent-server scenario is unchanged. The cost is the one a stalled open has (`docs/CLOSED_ITEMS.md`, "Cut the time a stalled open holds Kodi's UI"): a Stop pressed during a slow-but-healthy open now holds Kodi's UI for up to the rest of 30 s instead of 15 s. **Live check, 2026-10-12 (lab VM, Server-side mode, a real Kodi, one channel that starts in about 6 s):** a forwarder in front of the server answered the plugin's own "live playlist not found" reply for a set time after each `start_buffer` and passed everything else through (the plugin's file-server port forwarded as well, since segment URLs are built from the configured host). With no delay the channel played after 6.0 s. With 25 s of "not ready" it **played on the first try, at 29.7 s**; the pre-change build gave up at 15.6 s on three real channels that were slow to start (Kodi's playback-failed dialog each time). With 40 s it gave up at 29 s, logged `no live playlist after 60 tries and 29s, giving up`, and showed the dialog at 31.3 s; opening again with the delay off played in 5.2 s. A real channel whose ffmpeg had died stopped the wait on the plugin's `fatal` answer after about 24 s, as designed. **The freeze this costs, measured:** Stop pressed 5 s into a 40 s "not ready" open held Kodi's main thread for 26.4 s, until the loop gave up (JSON-RPC answered at once; any call needing the UI thread blocked). The item stays open until the reporter's mode and log are known. **What their answer decides:** (1) Server-side mode and `live playlist not found` in the log: this change covers it, and the item closes once they confirm on a build that has it (a slow channel that needs more than about 30 s would be the remaining case, and the log then says how long it took). (2) Server-side and `ffmpeg exited before producing any segments`: a different problem (a provider limit or a bad stream, the plugin's own fatal answer), not a slow start, and not fixed by waiting. (3) Off or Local mode: the addon only hands Kodi a URL (`BuildLiveChannelStreamProperties()`), so the playback error is Kodi's own or `inputstream.ffmpegdirect`'s and there is no addon line to find; nothing in the addon's open path applies, and the item becomes a question of whether the addon can warm the channel before handing the URL over, which needs its own design. The question to put to the reporter: which Live TV timeshift mode the addon is set to, and, with the addon's debug logging on, the Kodi log lines from one failed open of a slow channel (the lines mentioning `pvr.dispatcharr-unofficial` around the error), plus roughly how long the channel takes to start when it does play.

### Fix known, not yet done

#### Support Kodi 22 (Piers): the addon is refused by Kodi 22 RC1

**Opened 2026-10-12, from a user's report: on Kodi 22 RC1 (a Windows laptop) the addon "is not supported yet".** Kodi 22's PVR API is 9.2.0 with a minimum of 9.2.0 (Omega, which this branch builds against: 8.3.0, minimum 8.2.0), and its main and general APIs moved to 2.0.4 and 1.0.5, so the addon's declared imports and an Omega-built binary are refused outright; it must be rebuilt against Kodi 22's headers. A syntax-only compile of every `src/` file against the Piers dev-kit headers (branch `Piers`, 2026-10-11) gave six errors, all in `PVRDispatcharr.h`: the five recorded-stream overrides (`OpenRecordedStream()` now also returns a stream id, `ReadRecordedStream()`, `SeekRecordedStream()`, `LengthRecordedStream()` and `CloseRecordedStream()` take it), and `GetChannelStreamProperties()`, which gains a `PVR_SOURCE` argument (regular live, or playing a guide entry as live). The C++ wrapper hides the rest of the change (the C structs now hold string pointers instead of fixed arrays, EDL and timer-type lists are heap arrays), so most of `src/` compiles unchanged. What the port still needs: (1) the stream id means Kodi may hold more than one recorded stream open, but `DispatcharrClient` keeps one `m_recordingStream` and one `m_inProgressRecordingStream`, so either the state is keyed by id or a second open is refused deliberately; (2) the glue harness's stub and driver use the C structs directly and need the new shapes; (3) new optional calls worth a look, `GetRecordedStreamTimes()`, `IsRecordedStreamRealTime()` and `PauseRecordedStream()`, which bear on how an in-progress recording behaves in the player and on the open item about watching live while a recording runs; (4) `addon.xml.in` import versions, `KODI_COMMIT` and `KODI_BRANCH` in the workflow, and the Windows, Android and CoreELEC builds against Piers (`docs/BUILDING.md` notes `coreelec-22` tracks it); (5) the branching policy in `CLAUDE.md`: branch `Piers` off `Omega` once the source differs, keep `Omega` as the Kodi 21 maintenance branch, and decide how fixes flow between them (merge `Omega` into `Piers`; the six signatures are the only divergence so far). Confirm live on Kodi 22 RC1 with a Windows build: the addon loads, channels and guide appear, a live channel plays in each timeshift mode, a recording plays (completed and in progress) and seeks, and the timers dialog works.

### Architectural / concurrency

### Design decision needed

#### Watching live while a recording runs on the channel starts a second buffer

**Opened 2026-10-12, from a user's report (Server-side mode; they were recording a programme, then tuned the channel and answered "live" at Kodi's "play recording or tune to live" prompt).** `GetChannelStreamProperties()` and `OpenLiveStream()` never look for a recording on the channel: in Server-side mode every live open starts (or joins) the timeshift-buffer plugin's own buffer for it, a second ffmpeg and a rolling buffer on disk next to the recording's own. The user's expectation, from Tvheadend: the in-progress recording already allows pause and rewind, so watching live should use it and start no buffer. The cost today is the extra process and disk, not an extra provider connection (the buffer and the recording should both be clients of Dispatcharr's one proxy stream for the channel; not checked live). The idea is feasible in outline, since the addon already plays an in-progress recording with seek and pause (`OpenInProgressRecordingStream()`), but Kodi plays a channel through the live-stream callbacks (`OpenLiveStream()`, `ReadLiveStream()`, `SeekLiveStream()`, `GetStreamTimes()`) and a recording through the recorded-stream ones, so the live path would have to delegate to the recording's reader and report stream times for it. The blocking questions are semantic. (1) **The recording ends** at the programme's end plus post-padding, so a viewer who chose "live" reaches the end of the stream mid-channel; handing over to a timeshift buffer without a gap (or without Kodi leaving the channel) is not something the callbacks obviously allow, and a reopen drops the viewer to the channel with a gap. (2) **The recording can be stopped or deleted** (from Kodi or Dispatcharr) while someone watches it as live, which ends a stream they never asked to end. (3) **The live edge** of a recording is a segment or two behind the real one, as the timeshift buffer's is; rewind reaches back only to the recording's start, which is probably what a viewer wants. (4) **Tvheadend parity, checked in source 2026-10-13 (`docs/PVR_HTS_COMPARISON.md`, "Watching live while a recording runs"):** the report says Tvheadend plays the recording instead of starting timeshift when "live" is chosen over a recording; neither pvr.hts nor Tvheadend's timeshift code has any such behavior. pvr.hts asks for the maximum timeshift on every subscribe regardless of the DVR state, and the server's timeshift is per subscription and never looks at recordings. What can look like it: Tvheadend's optional on-demand timeshift (buffered only from the first pause), and the "Play recording" answer, which opens the in-progress file with pause and seek and ends playback when the recording ends. So Tvheadend is not a model for delegation with a handover; the closest it comes to the report's expectation is on-demand buffering. Options: leave it (it works, it costs a process and disk); a setting that plays the channel plainly (no pause or rewind) when a recording already runs on it, which saves the buffer but loses the pause the user wants; or the delegation above, preceded by a live experiment of what Kodi does when a live stream's reader returns end-of-stream mid-playback (does it leave, retry the open, or hold the player?), which decides (1). **Added 2026-10-13, from the reporter's follow-up and a read of Kodi's source (Omega tree, not yet confirmed live).** The reporter's expectation, restated: answering "live" should use the recording, not start a buffer, because the recording already allows pause and rewind; they used Tvheadend before, where choosing live while joining a recording starts no timeshift and plays from the recording. What the addon can see: nothing of the prompt. The prompt is Kodi's own (`CPVRGUIActionsPlayback::SwitchToChannel()`: "Play recording" or "Switch to channel"); "Switch to channel" starts an ordinary live open, indistinguishable from any other. The addon can find the recording itself (its recordings cache knows which are in progress on the channel). Today's workaround: answer "Play recording", which opens the in-progress recording with pause, seek and rewind, and skip to its end. **The end-of-stream question, answered from source:** when a live stream's read returns 0, `CInputStreamPVRBase::Read()` sets end-of-file, `CInputStreamPVRChannel::NextPVRStream()` then asks for a reopen, and `CVideoPlayer` closes the demuxer and breaks out of its loop, so **playback ends** (it neither retries nor holds). A live view delegated to a recording would therefore drop the viewer out of the channel when the recording ends (the programme's end plus post-padding), which is the common case for someone watching a programme live to its end; a plain delegation is not acceptable on its own. The addon controls the bytes `ReadLiveStream()` returns, and both the live buffer and an in-progress recording are byte-addressable lists of MPEG-TS segments in this addon, so a handover is possible in principle: start a timeshift buffer shortly before the recording ends and keep appending its segments to the same live address space (a discontinuity in the TS at the splice, which Kodi's demuxer already tolerates at the buffer's own restarts; to be confirmed). Open design choices: (a) leave it, with the workaround documented; (b) delegation with that handover (the largest option: detection, a live-callback wrapper around the in-progress reader, stream times, and the splice); (c) a setting that plays the channel plainly (no pause or rewind) while a recording runs, saving the buffer and losing the pause. **An on-demand buffer (start it at the first pause or seek) was analysed 2026-10-13 (`docs/TIMESHIFT.md`, "An on-demand live buffer: what it would take"; measured, nothing built):** the plugin can be started late with no change (first manifest 2.9 to 4.1 s after the call, a late buffer begins with roughly 10 s of recent past), but the addon would need a direct live reader that does not exist, a `PauseStream()` hook it does not implement, and a splice from the direct stream to the buffer; it saves a light `-c copy` ffmpeg and disk per viewer and gives the reporter only about 10 s of rewind at first, not the recording's, so it fits the cost they noticed and not the pause and rewind they want. Confirm the end-of-stream behavior live first (a live reader returning 0 mid-playback; the glue harness's ended-buffer knob and a real Kodi would do), then the splice. Confirm live with a recording running on a channel and the channel opened as live: today's behaviour is a buffer in `list_buffers` for that channel (the baseline to record), and after any change none, with pause, rewind and the recording's own end handled as decided.

#### Keep a title the user typed for a manual timer

**Opened 2026-10-11, left over from the untitled-recording fix (`docs/CLOSED_ITEMS.md`, the entry on a recording nothing titled).** `AddTimer()` keeps the title Kodi sends for three minutes (`PendingTitle`) and never writes it to the server, because the one write available, `RenameRecording()` (the `update-metadata` endpoint), stores `custom_properties.program.title` and marks the recording `user_edited`, which stops Dispatcharr's own later enrichment (description, poster, programme data) for it. For a recording Kodi named from the guide or the channel that is the right trade (enrichment supplies the title, the channel name stands in now), but a manual timer whose Name field the user typed loses that name after three minutes and shows the channel name instead. The difficulty is telling a typed name from Kodi's default: the default is the localized string "New Timer", which the addon cannot compare against reliably. Decisions: whether to persist the title for a manual timer (`timer.GetEPGUid() == PVR_TIMER_NO_EPG_UID`) only when it differs from the channel's name and from "New Timer" in the languages Kodi ships, or to persist it client-side in the addon's data like `RecordingEpgLinks` (survives restarts, not other Kodi clients), or to leave it. Confirm live with a manual timer named by hand: after the change the name must survive the three minutes and a Kodi restart, and a manual timer left at Kodi's default must still pick up the programme's title from Dispatcharr's enrichment.

#### Report a server that is not Dispatcharr to Kodi, and drop the restart warning

**Opened 2026-10-10 from the pvr.hts comparison; the login-driven part and the mid-session outage are done (`docs/CLOSED_ITEMS.md`, "Tell Kodi when Dispatcharr is unreachable or refuses the login" and "Tell Kodi when the server goes away mid-session"), this is what is left.** (1) **A server that answers but is not Dispatcharr** (a 404 or 405 from a proxy on the token path, a 200 with no token, a version endpoint with no version) is left unreported; Kodi has `SERVER_MISMATCH` ("Server does not respond properly") for it. The signals exist (`ReportForAuthFailure()` already sees the status; the startup version check sees a missing version), the open question is only which answers are unambiguous enough: a 404 on a path that exists on every Dispatcharr is, a 200 with an unexpected body from behind a captive portal may be, a transient 404 during a Dispatcharr upgrade is not. (2) **The "Restart Kodi to hide the record, delete and rename actions" warning** (`SyncDvrAccessFromDispatcharr()`) exists because Kodi reads capabilities once; since the held `CONNECTED` report now forces a re-read after the access level is learned, it may be removable, but nobody has seen Kodi's UI drop the actions without a restart. Confirm live with a view-only account (a disposable user on the lab server, which changes the lab: ask first) and the server unreachable at Kodi start, then reachable: the Record button, Timers window and delete/rename must disappear after "Connection established", and if they do the warning goes. Neither changes what a viewer sees often; (2) is the one with a concrete gain (no restart).

#### Let a series rule's title and description match modes be set from Kodi

**Opened 2026-10-10, from the pvr.hts comparison.** pvr.hts lets a timer rule match its title as "contains" or as a
regular expression (one global setting) and search the full EPG text per rule (`PVR_TIMER_TYPE_SUPPORTS_FULLTEXT_EPG_MATCH`).
Dispatcharr's series rule has `title_mode`, `description` and `description_mode` (confirmed shape in
`docs/API_NOTES.md`'s "Confirmed against a live instance" table); `src/TimerRuleParser.cpp` reads them back, but
`AddTimer()` creates every rule with them blank, so a rule made from Kodi always gets Dispatcharr's defaults and a rule
edited from Kodi keeps whatever it had. Decisions: whether the title mode is a global addon setting (pvr.hts's choice,
simplest) or per rule (Kodi's timer dialog has no match-mode field, so per rule would ride on the full-text flag);
whether Kodi's full-text flag maps to "also match the description" with the search string as `description`; and how
the four title modes are offered when Kodi has room for two. The values are confirmed from source (the Dispatcharr
source review, `docs/DISPATCHARR_SOURCE_REVIEW.md`): `title_mode` is `exact` (default), `contains`, `search` or `regex`;
`description_mode` is `contains` (default), `search` or `regex`; `untagged_is_new` is a separate boolean
(`SeriesRulesAPIView` in `apps/channels/api_views.py`). Confirm live by creating a rule from Kodi with each mode and
checking what Dispatcharr's web UI shows and which programmes it schedules.

#### List the two plugins in Dispatcharr's Plugin Hub

**Opened 2026-10-10, from the Dispatcharr source review; a decision about publishing, so it waits for the maintainer.**
Since Dispatcharr 0.23.0 an admin can browse, install and update plugins from repositories inside Dispatcharr, and the
official catalogue (the Plugins repository) accepts external plugins: a PR to its `main` branch adding
`plugins/<slug>/plugin.json` with `source_type: "external"`, a `source_url` that is an HTTPS link to a zip and contains
a `{version}` placeholder, `repo_url`, an OSI license (GPL-2.0-or-later qualifies) and `author` equal to the submitting
GitHub account; each version bump is another PR, reviewed by the catalogue's maintainers. Today both plugins install by
zip import only, and their zips are attached to addon-version releases, so no URL exists that is templated on the
plugin's own version. Options: per-plugin GitHub releases or tags cut by the release gate (satisfies the catalogue's
rule; Clapparr does this); a self-hosted repository manifest with absolute `latest_url`s, updated by the gate (the flat
format in Dispatcharr's `Plugin_repo.md`; users add its URL once; the name must not contain "official" or
"dispatcharr"); or staying with zip import. Either hosted option means the release gate also writes a manifest and
checksums, and the privacy gate must cover what it publishes. Decide first; the mechanics follow.

#### Use Dispatcharr's event hooks in the plugins

**Opened 2026-10-10, from the Dispatcharr source review.** An action whose definition carries an `"events": [...]` list
is run by `log_system_event()` when one of those system events fires (`iter_actions_for_event` in
`apps/plugins/loader.py`); the names are `channel_start`, `channel_stop`, `channel_buffering`, `channel_failover`,
`channel_reconnect`, `channel_error`, `client_connect`, `client_disconnect`, `recording_start`, `recording_end`,
`stream_switch`, the `epg_*` and login events, `vod_start` and `vod_stop`. Handlers run on a gevent greenlet under uWSGI
and must stay short. Neither plugin subscribes to anything. Candidates: `timeshift_buffer` reacting to
`channel_failover`, `channel_error` or `stream_switch` on a channel it is buffering (its dead-ffmpeg handling is a poll
today, `docs/TIMESHIFT.md`), and `recording_edl` running its sidecar scrub on `recording_end` instead of only on demand.
Decide per plugin whether an event hook adds anything a poll does not, keeping in mind the handler cannot block and the
event may arrive on a different worker than the one holding the buffer's state (Redis is the shared state, as today).
Confirm live by watching the plugin log while a stream fails over on a buffered channel and while a recording finishes.

### Known gaps, deliberately deferred

#### Wake-on-LAN for a Dispatcharr host that sleeps

**Opened 2026-10-10, from the pvr.hts comparison; deferred.** pvr.hts sends a Wake-on-LAN packet to a configured MAC
address (`kodi::network::WakeOnLan`, part of Kodi's addon API) before its first connect, for a backend that sleeps when
idle. Cheap to add as an optional setting, but Dispatcharr is usually a container on an always-on host and nobody has
asked. Pick it up if a user reports a sleeping server; the whole change is the setting, one call before the first
request, and a note in the README.

#### Multiple Dispatcharr servers from one Kodi

**Opened 2026-10-10, from the pvr.hts comparison; deferred.** Kodi 20 and later let one PVR addon run several backend
instances (`instance-settings.xml` next to `settings.xml`); pvr.hts added it in 20.4.0 with a one-time migration of the
pre-instance settings in its `addon.cpp`. This addon is one instance, and `docs/API_NOTES.md`'s "Single-instance
assumption: partially hardened, not fully" section lists what else assumes that (the API-key persistence, the recurring
rule tag). Worth doing only if someone runs two Dispatcharr servers, or wants two accounts (admin for the companion
plugins, non-admin otherwise) against one server from one Kodi; the migration step and the per-instance settings
handling in `OnAddonSettingChanged()` are the work. Not started.
